# Pilot B v2 execution wiring

This revision changes orchestration and observation only. Execution remains
paused. Fresh explicit approval bound to the final review seal/report and the
cumulative resource ceilings is required. The original stopped Pilot B v1,
unexecuted v1 draft, FAILED overall qualification and FAILED 0.001 agreement
criterion remain unchanged.

The authoritative comparison is the sealed counterfactual v1 preflight:
ID 0, step zero, nominal menu 4 and alternative menu 3, frozen binary64 request,
RPM, force and torque records, exact rational >=5% separation. No new candidate
selection or threshold is introduced. Native MPC80, solver settings, model,
assets, task, references, controller information and warm starts remain unchanged.

The new entrypoint is `experiments/12_counterfactual_pilot_b_v2.py`. Its
`dry-dispatch` mode uses the same reservation/dispatch supervisor as execution,
with inert jobs under blocked real optimizer and simulator APIs. Dry receipts
are marked as such and never debit the scientific ledger. `execute` requires a
fresh approval file and a new output directory. It verifies the review seal,
copies unchanged branch configurations, freezes source/configuration identities,
and binds approval to the prospective ledger. No approval is generated by this
review. Existing stopped/completed/partial attempts cannot resume automatically.

Each scientific worker preserves native construction/controller-reset/plant-reset
order. The original first query is independently captured and checked before
archive parity and detached substitution. Nominal requires all 300 archived
queries; alternative requires the first only. Returned actions are detached
copies; optimizer primal/dual, guesses, x/u plans and native history are not
replaced with archived solutions during real execution. Reference steps 0–299,
terminal preview and native x-column/u-row shifts are preserved. One native
query occurs per step. Candidate-specific reserves use the actual detached
request and current raw/cache state.

Current motor API arguments and force/torque submissions are journaled before
integration. The v2 boundary observer checks actual and RPM-derived inputs and,
for all first-interval alternative submissions, exact frozen request/clipped/RPM/
force/torque bytes and separation. A mismatch stops before the next physics
step, retaining the submitted packet and incomplete record. These are directly
recorded API arguments; derived thrusts are distinct and no physical sensor
outputs or unobserved engine internals are claimed. Passive reset-context
comparisons now preserve signed-zero bytes. Startup exceptions also retain an
explicit failure record. The v2 solve hook is scoped to the one expected Opti
instance and is restored on exit.

Order is the original 12-job plan: nominal original + native/motor replays,
nominal repeat + both replays, then the corresponding alternative jobs. Both
nominal scientific runs must match the archived scientific arrays and all
candidate vectors, their deterministic repeats and both replays before any
alternative reservation. All runs require complete 300-control/6,001-state
records, strict nonnegative raw margins, zero contacts, unchanged v2 KKT/program/
finite-value checks, positive causal reserves and source closure <=1e-10.
Incomplete or unverified is never safe. Both branch repetitions and the two
replay types use the accepted checks. Uninstrumented native replay compares
301 control states/rewards and end-interval RPM; instrumented motor replay also
checks all 6,001 raw states/contacts and direct submissions. Do not claim that
the uninstrumented replay directly captures every physics sample.

All jobs reserve before dispatch. The first failure halts the campaign without
fallback, retry, overwritten evidence or reservation refund. Full available
candidates, diagnostics, nonfinite values, status, timing and partial histories
are retained by the accepted guard/journals plus v2 startup/supervisor records.
Parent and child execution CPU and active wall, startup, preparation, hashing,
verification and replay overhead are charged. One worker, 4 GiB and native
one-second action watchdog remain fixed. Each job has a cumulative remaining-wall
timeout and child CPU limit. Original remaining allowances are 3,070 solves and
366,000 physics steps. Full Pilot B reserves 1,200/72,000, leaving 1,870/294,000.
The proposed additional 300 CPU/600 active-wall seconds must begin after the
final review charge; exact ceilings are recorded in the sealed review ledger.
This is a finite prospective proposal, not an authorized allocation.

Zero-solve tests exercise the exact CLI, shared dispatch loop, every job's first-
failure stop, preparation/worker routing, pre-physics checks, passive reset bytes,
startup failures, and real wrapper with scripted archived native MPC flow. Such
fixtures provide no live trajectory-equivalence or safe-alternative result.
A successful technical pilot would validate execution fidelity only, not the
original three-of-four action-support or beyond-expert performance criteria.
