## 1. Main research direction

The broader area is safe reinforcement learning for nonlinear control.

A major prior direction is safe RL via diffeomorphic/state-barrier transformations. The user's earlier work includes safe RL for power-electronics control and later extension toward drilling control.

The current drilling research question has evolved toward:

> Can a learned controller improve upon an existing barrier-LPV drilling controller using data generated by that controller, while preserving or improving safety?

The advisor prefers a direction centered on offline RL from data collected using the physical/existing controller, not merely imitation.

A newer advisor idea is:

> During learning, can the learner identify risky, uncertain, or poorly covered operating regions and ask the existing controller to collect additional data specifically in those regions?

Once new data are requested, this is no longer strictly fixed-dataset offline RL. It is closer to active data collection / iterative batch RL / active expert querying around an offline-RL core.

## 3. Drilling safety constraints

Desired bit velocities:
- axial velocity: `v_d = 0.001 m/s`
- rotational speed: `w_d = 10 rad/s`

Rotational error:
`e_w = w_b - w_d`

Bounds:
- `k_wl = -4.77`
- `k_wu = 5.7`

Therefore absolute bit rotational speed must remain:

`5.23 < w_b < 15.7 rad/s`

Axial error:
`e_v = v_b - v_d`

Axial bounds are state-dependent:

`K_vl(e_w) < e_v < K_vu(e_w)`

The transformed axial and rotational errors are used by the LPV controller as scheduling variables.

## 5. Offline RL direction

Advisor preference:
- learn from logged data generated by the physical/existing controller
- do not rely only on simulation
- do not merely mimic the controller
- aim to improve performance/safety

Behavior cloning asks:
> What action did the LPV controller take?

Offline RL asks:
> Among supported state-action trajectories in the dataset, which actions lead to better long-term outcomes?

Planned literature direction:
- IQL first
- then CQL / TD3+BC / offline constrained RL as relevant

Important limitation:
- if the expert dataset is nearly deterministic and concentrated around nominal operation, the learner may have insufficient action diversity/support to improve beyond the expert
- richer data should include different initial conditions, operating points, uncertainties, disturbances, and near-boundary states

Typical offline transition:
`(s_t, a_t, r_t, s_{t+1})`
plus safety margin/cost, reference, operating condition, and other relevant context.

## 6. Literature already reviewed

### Residual Reinforcement Learning for Robot Control — Johannink et al.
Core idea:
`u = pi_H(s) + pi_theta(s)`

A conventional controller handles known behavior; RL learns an additive correction for hard/unmodeled effects.

Important:
- still interacts online with the environment
- not fixed-dataset offline RL
- learned residual does not automatically inherit formal safety guarantees

### Residual Reinforcement Learning from Demonstrations — Alakuijala et al.
Core idea:
1. behavior cloning from demonstrations produces a base policy
2. freeze the base
3. learn an additive residual policy

`u_final = pi_b(s) + pi_r(s,u)`

Important:
- residual stage still uses environment interaction
- therefore not the same as the advisor's offline-only direction

The next offline-RL paper planned for study is IQL.

## 7. Active expert-query idea

Conceptual loop:

`initial offline dataset`
`-> learner identifies uncertain/risky region`
`-> learner requests expert/controller rollout there`
`-> add data`
`-> retrain`
`-> repeat`

Uncertainty and risk are separate.

Proposed uncertainty measure:
- train an ensemble of learned policies on bootstrap samples of the initial dataset
- evaluate all policies at a candidate state
- use policy disagreement as epistemic uncertainty

For policies `pi_1, ..., pi_N`:

`U(s) = Std[pi_1(s), ..., pi_N(s)]`

Safety criticality is determined separately from the safety margin.

Possible query principle:
- high uncertainty
- small positive safety margin
- optionally large distance from existing dataset

Important caveat:
- the expert/controller itself may fail in some regions
- therefore expert exploration cannot assume the teacher is universally safe

## 8. Pendulum-v1 proof-of-concept

Purpose:
Test active expert-query logic in a simple continuous-control environment before returning to drilling.

Environment:
`Pendulum-v1`

Internal state:
`x = [theta, omega]`

Gym observation:
`[cos(theta), sin(theta), omega]`

Action:
continuous torque clipped to:
`u in [-2, 2] N*m`

Target:
- `theta_d = 0`
- `omega_d = 0`

### PD expert

Controller:
`u = -Kp*theta - Kd*omega`

Parameters:
- `Kp = 8`
- `Kd = 2`
- max torque = `2 N*m`

The PD controller plays the role of the existing drilling LPV controller.

### Safety constraints

- `|theta| <= 1 rad`
- `|omega| <= 3 rad/s`

Normalized safety margin:

`m(s) = min(1 - |theta|/1, 1 - |omega|/3)`

Interpretation:
- `m > 0`: safe
- `m = 0`: boundary
- `m < 0`: violation
